# FounderFit Candidate Assessment

FounderFit is a two-sided founder–asset matching tool. Rather than asking whether someone is a good founder in general, it evaluates whether a candidate is the right founder for a specific, already-validated technology asset.

Candidates are measured on three groups of dimensions:

- **Disposition (P1–P9):** stable traits that a venture has to be designed around, such as ambiguity tolerance.
- **Capability (C1–C8):** learnable competencies that close in 90–180 days with support, such as market translation.
- **Adjacency (J1–J5):** the candidate's position relative to this asset, such as domain credibility and buyer-market access.

## Features

- **Assessment flow:** timed forced-choice blocks, situational-judgment scenarios, calibration items, and assessor-rated adjacency.
- **Deterministic scoring:** a fit index (FFI), band, gates, gaps, risk flags, and a recommended configuration, computed in the browser.
- **Google sign-in with an allowlist:** every user signs in with Google; only verified accounts on the allowlist can use the app, and each user can only see and change their own assessments.
- **Saved reports:** each completed assessment (including every re-score) is saved to Cloud Firestore.
- **AI narrative:** an optional written report generated by Gemini on Vertex AI through a server route, with a deterministic fallback when the model is unavailable.
- **PDF export:** print styles produce a clean report via the browser's "Save as PDF".

## Data model and security

Assessments are stored at `users/{uid}/assessments/{assessmentId}`. Each document holds the candidate name, asset, score, band, validity status, versions, the context answers (`K1`–`K10`), the full scoring report, the narrative (initially `null`), and server timestamps.

The rules in `firestore.rules`:

- allow a signed-in user to read, create, and delete only their own assessments;
- require the exact set of fields on create, with type and range checks;
- allow only the `narrative` and `updatedAt` fields to change after creation;
- deny all client access to `narrativeUsage` (server-side rate-limit counters);
- deny everything else.

The narrative route keeps the prompt on the server and checks, in order:

1. a valid Firebase ID token, otherwise `401`;
2. a verified email on the allowlist (see below), otherwise `403` with `{ error: "forbidden", reason, message }`;
3. a body of at most 200 KB (`413`) that is valid JSON of the expected shape (`400`);
4. the caller's daily limit, otherwise `429` with `Retry-After`. Each call that reaches the model counts, including failed ones. If the counter can't be read, production answers `503` (development lets the call through).

### Access allowlist

Anyone with a Google account can sign in with Firebase Auth, so the app decides who may actually use it. An account is allowed when its email is verified (`email_verified` in the ID token) **and** it matches `FOUNDERFIT_ALLOWED_DOMAINS` (exact domain, e.g. `sciencewerx.org`) or `FOUNDERFIT_ALLOWED_EMAILS` (individual addresses). Both are comma-separated and case-insensitive.

**If both are empty:** production (`NODE_ENV=production`) allows nobody, so a missing config never opens the paid model to every Google account; development allows any verified account so local work needs no setup.

Right after sign-in, `AuthGate` calls `GET /api/access`. A `403` shows a "this account isn't allowed" screen with a sign-out button; the same screen appears if `/api/narrative` answers `403` later (for example after the allowlist changes). If the check itself fails (network, 5xx) the app still opens, because the server enforces the allowlist on the paid route.

**Limitation:** Firestore rules can't read environment variables, so the allowlist is not enforced on Firestore writes. A signed-in account that is not allowed could still use the Firebase SDK directly to create assessments in its own `users/{uid}` path (nobody else's), at the cost of a few document writes; it can't reach the model. Closing this would need the allowlist duplicated in `firestore.rules` (e.g. `request.auth.token.email.matches(...)`) or custom claims set by the server.

### Daily narrative limit

Each user may call `/api/narrative` `FOUNDERFIT_NARRATIVE_DAILY_LIMIT` times per UTC day (default 30). Counters are stored at `narrativeUsage/{uid}_{YYYY-MM-DD}` by the Admin SDK in a transaction, so the limit holds across instances. Each doc has an `expireAt` field: to delete old counters automatically, add a Firestore TTL policy on `narrativeUsage.expireAt` (optional).

## Local setup

1. Install dependencies:

   ```bash
   npm ci
   ```

2. Create `.env.local` from the example and fill in the Firebase web app config (Firebase Console → Project settings → Your apps → *FounderFit Web*):

   ```bash
   cp .env.local.example .env.local
   ```

3. Start the development server:

   ```bash
   npm run dev
   ```

   Open http://localhost:3000 and sign in with Google. `localhost` is an authorized sign-in domain by default.

In development, the intro and header show sample-candidate buttons and the results page shows the save status. Both are hidden in production builds. Add `?fsdebug` to the URL to print Firestore debug logs in the browser console.

| `NEXT_PUBLIC_FIRESTORE_EMULATOR_HOST` | browser | no | **Local development only.** Points the app at a local Firestore emulator, e.g. `127.0.0.1:8085`. |

Never commit `.env.local`, never prefix `GEMINI_API_KEY` with `NEXT_PUBLIC_`, and never add it to `apphosting.yaml`.

## ScienceWerx Connect

ScienceWerx apps (Prism School, iStartup, FounderFit, InkKeep, InkGuard) each keep their own database and sign-in, and share a small summary of the same person **server to server**, matched by **verified email**. An app only ever asks about the person signed in to it right now; there is no listing or search of other people. Browsers never call a peer: they call their own app's `/api/connect/peers`.

**FounderFit as a provider.** `GET /api/connect/v1/summary` with `Authorization: Bearer swc_…` and `X-Connect-Subject: person@example.com`. The key's SHA-256 must match a `CONNECT_CALLERS` entry with the `summary` scope (401/403 otherwise; 400 for a malformed subject). The subject's Firebase account must exist with a verified email and have at least one assessment, otherwise the answer is `200 {"found": false}`. The card shows the latest assessment's FFI score and band (plus validity when not clean), its date, and up to five lines: venture, candidate, strongest area, biggest gap, fit pattern. The narrative and the raw report are never returned. Calls are logged with the caller name and a hash of the subject, never the email.

The provider does **not** check FounderFit's allowlist (`FOUNDERFIT_ALLOWED_*`). The allowlist decides who may use FounderFit; a Connect summary is the person reading their own existing result inside another ScienceWerx app that has already verified their email, and it grants no access to FounderFit itself.

**FounderFit as a consumer.** `GET /api/connect/peers` needs a Firebase ID token whose email is verified and on the allowlist. It calls iStartup's summary and Prism School's and iStartup's certificates in parallel (4 s timeout each, redirects not followed), checks and caps every field, and returns `{ cards, certificates }`. A peer that is unconfigured, down, slow or refusing is just missing. The "Connected apps" panel on the home screen shows the result and is hidden when there is nothing.

**Setup.** Generate this app's key and give its SHA-256 to the apps that should accept it:

```bash
node -e 'console.log("swc_" + require("crypto").randomBytes(32).toString("base64url"))'   # CONNECT_KEY (secret)
node -e 'console.log(require("crypto").createHash("sha256").update(process.argv[1]).digest("hex"))' swc_...   # for their CONNECT_CALLERS
```

In production, store `CONNECT_KEY` with `firebase apphosting:secrets:set CONNECT_KEY` and grant the backend access, then uncomment the Connect entries in `apphosting.yaml`. Leave the `CONNECT_KEY` entry commented until the secret exists, or the rollout fails. With nothing configured, Connect is off: FounderFit calls nobody and answers every caller with 401.

## AI narrative locally

The narrative route calls Gemini in one of two ways:

- **Vertex AI (default, same as production).** Sign in with Application Default Credentials. Your account needs permission to call Vertex AI (`roles/aiplatform.user`):

  ```bash
  gcloud auth application-default login
  gcloud auth application-default set-quota-project founder-fit-6a455
  ```

- **Gemini Developer API (optional).** Set `GEMINI_API_KEY` in `.env.local` with a key from Google AI Studio.

If the call fails, the report shows the deterministic fallback narrative instead.

## Tests

```bash
npm test                 # unit tests: narrative route, allowlist, daily limit, access check, Gemini client, ScienceWerx Connect (mocked, no network)
npm run test:firestore   # Firestore rules, save, daily-limit counter and Connect summary read tests in the local emulator
```

`npm run test:firestore` starts the Firestore emulator under the offline project ID `demo-founder-fit` on port 8085, so it never touches the real database. It needs the Firebase CLI and Java 21+.

To try the full app against the emulator instead of the real database:

```bash
firebase emulators:start --only firestore --project founder-fit-6a455
# then set NEXT_PUBLIC_FIRESTORE_EMULATOR_HOST=127.0.0.1:8085 in .env.local and run npm run dev
```

## Deployment (Firebase App Hosting)

The app is deployed by the App Hosting backend **`founder-fit`** in **`us-east4`**, connected to this GitHub repository:

- **URL:** https://founder-fit--founder-fit-6a455.us-east4.hosted.app
- **Root directory:** `/`
- **Runtime:** `nodejs22`
- **Rollouts:** automatic on every push to the live branch

`apphosting.yaml` defines the run config (0–2 instances) and the environment variables above, including the allowlist (`FOUNDERFIT_ALLOWED_DOMAINS=sciencewerx.org`) and the daily limit. It contains no secrets: on App Hosting, Vertex AI is called with the backend's service account, `firebase-app-hosting-compute@founder-fit-6a455.iam.gserviceaccount.com`, which needs `roles/aiplatform.user`.

### Deploying Firestore rules and indexes

Rules and indexes are not deployed by App Hosting. After changing `firestore.rules` or `firestore.indexes.json`, run the emulator tests, then:

```bash
firebase deploy --only firestore --project founder-fit-6a455
```
